# Decisions

This file records the decisions that the maintainer made while reviewing these notes on
2026-10-19, 2026-10-22, 2026-10-23, 2026-10-26, 2026-10-28 and 2026-10-29. It also lists the
questions that stay open. The other documents follow this file. If a document disagrees with it,
this file wins.

"Settled" marks a choice of the maintainer. "Recommendation" marks a proposal of these notes that
the maintainer has not confirmed yet.

## Extension types

### Settled

| ID | Decision | Reason |
| --- | --- | --- |
| X1 | Extension types are opaque by default. No code applies storage semantics to an extension value unless the type opts in | Storage semantics give wrong results for most types (EXT-Q2, EXT-C2) |
| X2 | A claim (`Eq` or `Ord`, X13) is a property of one extension dtype. It never applies across dtypes | Two dtypes with different metadata are different types |
| X3 | Engines convert operands to a common dtype. Vortex runs only operations whose operand dtypes already match | Engines already do this in their planners, and one owner avoids two rule sets that disagree |
| X4 | A type implements its behavior as rewrite rules on arrays. The rules are registered with the type, together with its compression scheme and the other parts of the type. There is no `ext_wrap` expression | A rule builds its result array directly, so a separate wrap expression adds nothing |
| X5 | A rewrite rule pulls generic structural arrays, such as `Constant` and `Dict`, out from under the extension wrapper | Code that looks for a constant or a dictionary then finds it at the top, without any knowledge of extension types |
| X6 | Extension values inside a struct, list or map are handled by removing extension layers at every depth. Nested kernels get no extension code | Kernels then see storage dtypes only |
| X7 | `ExtensionArray::try_new` checks every non-null value. A new `ExtensionArray::new_unchecked` skips the check for kernels that keep legal values | Today arrays are never checked (EXT-V1). This is a bug |
| X8 | API changes are acceptable where correctness needs them, for example fallible constructors and private enum variants | Correctness and clear abstractions matter more than the current API |
| X9 | Whether a validity query raises the errors of values that it skips is out of scope here | Issue [#10313](https://github.com/vortex-data/vortex/issues/10313) owns this question, and it is not specific to extension types |
| X10 | `ExtensionStoragePushdown` ([#10566](https://github.com/vortex-data/vortex/pull/10566)) computes an aggregate on storage correctly, but it does not stay a separate aggregate. Its body becomes the default storage path of aggregate binding (X21). Its composite IDs and `register_storage_ordered` ([#10616](https://github.com/vortex-data/vortex/pull/10616)) go away | Consumers such as zone maps and engine pushdown ask for the plain IDs, so an opt-in that needs a composite ID reaches only tests. The registrations are written by hand, and nothing checks them. [Part 3](extension-types/03-design.md#aggregates) explains the change |
| X11 | An extension type author can opt in to common behavior, such as equality and order, with little code. Claims (X13) are the mechanism. They replace the `Derives` flags sketch | One line in the vtable of the type is enough. X2 still holds: a claim covers values of one dtype |
| X12 | Each result of `ExtensionStoragePushdown` that is a value of the input gets the extension dtype back inside the adapter, before the adapter returns it. Today the adapter returns raw storage values | A storage result loses the metadata of the type, for example the time unit and time zone of a timestamp. Nothing wraps the result later, and plain `min_max` already wraps its results (EXT-A3) |
| X13 | A claim is a promise that an extension type makes about its storage: one kind of operation gives the same answer on the values and on their storage values, in both directions. `Eq` means that two values are equal exactly when their storage values are equal. `Ord` means that the value order is the storage order, and it implies `Eq`. An extension type is opaque unless it makes a claim. Each type lists its claims by hand in `ExtVTable::claims`, and the default is no claims. Claims are never derived from which `=` or `<` kernels exist. Built-in dtypes hold claims by a fixed table: `Null`, `Bool`, `Primitive`, `Decimal`, `Utf8` and `Binary` hold both. `Struct`, `List`, `FixedSizeList` and `Map` hold a claim when their children hold it. `Union` and `Variant` hold neither. A type stored as floats inherits the float semantics of Vortex: a total order and bitwise equality | Kernels are registered per encoding, not per dtype, so a missing kernel would silently remove a claim. A type with its own `=` rule still cannot claim `Eq`, because `group by` and hashing run on storage. The built-in table follows what compare supports today (`vortex-array/src/scalar_fn/fns/binary/compare/mod.rs:206-219` at `c56ee8803b`) |
| X14 | The claims are `#[non_exhaustive] pub enum Claim { Eq, Ord }`, with `Claim::implies` and `DType::holds(Claim)`. A claim defined outside Vortex needs a struct with statics later. That switch is a mechanical change of interfaces, and the logic stays the same | Start simple. Only a third-party claim needs the open form, and none exists yet |
| X15 | `ExtDType::try_with_vtable` checks that the storage dtype holds every claim of the type, and that the claims are the same for both nullabilities. Typing then checks only the top-level dtype of an argument with `DType::holds` | A claim is valid only if the storage holds it. The check is linear in the size of the dtype tree and stops at nested extension dtypes, which were checked when they were built. So nested extension types need no extra work in typing |
| X16 | `Date`, `Time`, `Timestamp`, `Uuid` and `Duration` (#10467) claim `Eq` and `Ord`. `Uuid` orders by its bytes. `Vector` and `FixedShapeTensor` claim `Eq`. `Json`, WKB, the native geometry types, `ForeignExtDType` and `Interval` (#10468) claim nothing. `Interval` waits until its PR decides what interval equality means. This settles XQ6 | One dtype fixes the unit of a temporal type. Byte order is the hex text order and the Postgres order, and for UUIDv7 it is also time order. `Json`, WKB and geometry values can have several storage forms. Spatial equality is topological |
| X17 | Each scalar function and aggregate has one method, `extension_use(options, arg_dtypes) -> ExtensionUse`, that typing calls once for each call. The answers are `None`, `Structural`, `Specific`, and `Storage { claims, result }`. `None` is the default, and it rejects extension operands unless a rule of the type covers the call. `Storage` names the claim that each argument needs. An argument that is only moved needs no claim. A part of an argument that needs another claim becomes a separate argument, for example through `get_item`. There is no list of built-in functions. The documentation must explain `Specific` and `None` well | A function that accepts any dtype, such as a hash of storage bytes, would apply storage semantics by default without the `None` default. A function sees all argument dtypes at once, which it needs for the result mapping (X19) |
| X18 | `Structural` functions, such as `zip`, `case_when` and `fill_null`, run on storage and get the dtype that their own `return_dtype` gives. Their value operands already need one dtype, ignoring nullability. Functions that never look inside an operand, such as `get_item` and `is_null`, need nothing. `Storage` functions, such as compare, `between`, `list_contains` over lists of extension values, `min`, `max`, `min_max`, `is_sorted`, sorting and the row encoding, run on storage when the claims hold. Other functions that read values, such as `byte_length` or `like` on `Json`, are rejected until a new claim covers them. `Specific` functions, such as `replace_time_zone`, the spatial functions and `json_to_variant`, handle their types themselves | A structural function never reads a value, so storage gives the same result. A function written for a few types names them in its own `return_dtype` and works on the extension array directly |
| X19 | `Storage` carries the result mapping, so the compiler forces every function that runs on storage to give one: `ResultMapping { Rewrap(ExtDTypeRef), Keep, Fields(Vec<ResultMapping>), Custom(Arc<dyn CustomMapping>) }`. `Rewrap` wraps the storage result in the given extension dtype. When the call is built, its guard checks that the storage result dtype equals the storage dtype of the target, ignoring nullability. The result keeps the nullability of the storage result. `Rewrap` trusts the values and uses `ExtensionArray::new_unchecked`, and debug builds run the value check. A claim that allows `Rewrap` must guarantee legal results. This settles XQ5 | A wrong mapping cannot compile in, and the guard catches a wrong dtype early. `Eq` and `Ord` results are input values, so they are legal. A future arithmetic claim can overflow, so it needs a checked mapping. `Fields` covers `min_max`, and `Rewrap` with a dtype covers a result that is part of an input, such as one element of a list |
| X20 | The rules of a type (casts and kernels for functions) live on `ExtVTable`, written over `ReduceNode`. Only the crate of the type adds rules for the type, as with the orphan rule of Rust. A rule of the type wins over the default storage path. This settles XQ2 | The rules travel with the dtype, so the static optimizer, pruning and the executor find them with no session. A session registry would bring back conflicts between crates and rules that plain `.optimize()` calls miss |
| X21 | Aggregate binding (`AggregateDTypes::try_new`) takes the default storage path for an extension input whose aggregate answers `Storage` and whose claims hold. It runs the body of today's adapter under the plain aggregate ID. A partial state stays in storage form in memory. It gets the logical form when it leaves the accumulator: `finalize`, `finalize_scalar` and `to_scalar` wrap, and `partial_from_scalar` unwraps. This replaces the mechanism of X10 | Zone maps, cached statistics and engines see the plain IDs and the same partial dtype as today. Wrapping costs a constant amount for each partial, never for each row. Plain `min_max` already wraps after each batch today |
| X22 | Zone maps keep logical `Min` and `Max` for extension types that claim `Ord`, so their format does not change. They write no min and max for other extension types, so the storage fallback goes. The null count stays, and a type can add its own statistics through its own aggregates, as the spatial bounding boxes of #10837 do. Readers ignore stored min and max of an extension type without `Ord` in every place that reads them, and they log a warning once for each file and column | A logical min of an `Ord` type holds its storage min, so pruning reads either. Vortex has stored storage-order min and max for every extension type for at least a year (EXT-A2). They are useless after the change, but old files hold them. A type that gains `Ord` later can use its old statistics, because `Ord` means storage order |
| X23 | Deserialization runs only the structural `VTable::validate`. The value check of X7 lives in `ExtensionArray::try_new` only, never in `Extension::validate`. An optional strict read mode checks values. The extension type adds no rule about null slots: the storage array must be a valid array of its own encoding, and the value check reads only non-null slots. This settles XQ3 and XQ4 | Every deserialize ends in `Array::try_from_parts`, which calls `VTable::validate` (`vortex-array/src/array/plugin.rs:194` and `vortex-array/src/array/typed.rs:241-243` at `c56ee8803b`). Several encodings use unchecked constructors in `deserialize`. A storage encoding such as `VarBinView` already decides what a null slot can hold |
| X24 | Every boundary keeps the extension type or fails. Storage leaves only through `ext_storage`. Arrow and DataFusion export a type without a plugin as its storage with `ARROW:extension:name` set to the Vortex ID and `ARROW:extension:metadata` set to its metadata, and import recognizes Vortex IDs. DuckDB, Python and JNI use a converter for each type, or fail. Engine pushdown reads the claims. New plugins fill the gaps that the implicit conversions leave | Today Arrow export fails without a plugin, but a storage-like target type leaks storage (EXT-B2). DataFusion, Python and JNI leak storage, and DuckDB decides pushdown from the storage type (EXT-B1, EXT-B3 to EXT-B5) |

X1 to X9 date from 2026-10-19, and X10 to X12 from 2026-10-29. A design pass later on 2026-10-29
settled XQ2 to XQ7, added X13 to X24, and changed X2 (wording), X10 and X11.

## Decimal and new physical types

Issue [#10701](https://github.com/vortex-data/vortex/issues/10701) tracks the fix of the canonical
decimal encoding.

### Settled

| ID | Decision | Reason |
| --- | --- | --- |
| D1 | `Decimal` stays a built-in type. It behaves like a hardcoded extension type: opaque by default, with derives for one dtype and rules that the type owns. If the two become identical, a later change can remove the built-in type | A move to an extension type adds no capability, and the built-in type can follow the same rules |
| D2 | A canonical decimal array is a leaf with one buffer and validity. It has no data child | A leaf is simpler than a wrapper over an integer child, and it is the same as the `vortex.decimal` wire node |
| D3 | Each decimal dtype has exactly one canonical encoding. The precision fixes the width of the buffer | Today one dtype has six physical forms, which causes the crashes in issue [#5820](https://github.com/vortex-data/vortex/issues/5820) |
| D4 | A `Widen` encoding stores a decimal column as a child with a lower precision and the same scale | Without it, D3 forces the full width on every column, which costs performance |
| D5 | Vortex adds `I128`, `I256`, `U128` and `U256` as primitive integer types | Wide decimals need an integer view, and wide integers are useful as columns |
| D6 | FixedSizeBinary becomes a core type for opaque bytes of a fixed length, such as UUIDs and hashes | Its defining operations (equality, hashing, byte order, cheap scalars) are core operations. Arrow and Parquet have it natively |
| D7 | `vortex.decimal` keeps its wire ID. A reader finds an old node when its stored width differs from the canonical width of its dtype | D3 removes forms and adds none. The versioning spec asks for a new ID only when readers must understand something new |
| D8 | One `Widen` encoding, with one `vortex.widen` wire ID, covers integers and decimals. Integers narrow by width (issue [#10020](https://github.com/vortex-data/vortex/issues/10020)), and decimals narrow by precision. The metadata stores only the child `PType` of an integer child, or only the child precision of a decimal child, in a prost message with a typed `oneof` (D32). It stores no scale and no nullability. This settles DQ2 and DQ3 | A release that permits an ID must read every valid instance of it. So the decimal reader ships in the same release as the first edition that permits `vortex.widen`. The child must have the scale and nullability of the parent, so metadata that stored them would only let a file hold an invalid child. The format is in no edition yet, so it can still change |
| D9 | A reader converts an old `vortex.decimal` node, whose stored width differs from the canonical width of its dtype. One rule covers every such width, through `WidenArray::from_stored_decimal` (D40). The reader scans the valid values for their min and max, and it chooses the smallest precision that the values and the scale allow. The result is a `Widen` over a child at the canonical width of that precision, or the canonical array when that width is the canonical width of the column. The child reuses the buffer when its width is the stored width, and copies it otherwise. So a node stored wider than its canonical width can also become a `Widen`. A narrowing copy follows D21 | A width does not give a precision. The read plugin cannot use stored statistics, because the deserializer attaches them after the plugin returns. Old nodes are rare, so the speed of this path matters little. One rule for every width keeps one owner of the child label (D40) |
| D10 | A decimal `Widen` child has the same scale and nullability as its parent, and a canonical width strictly narrower than the canonical width of the parent. The producer chooses the child precision: the best precision that the values and the scale allow, or a larger one | A `Widen` that does not reduce the width has no use. The integer `Widen` has the same rule. The rule can be relaxed later |
| D11 | The canonical-width work lands as an in-memory change, and then as a wire change (D18). Each step of the in-memory change is its own PR, because none of the steps needs temporary code. The wire change lands in lockstep, if possible in the same release as the in-memory change. PRs [#10305](https://github.com/vortex-data/vortex/pull/10305) and [#10314](https://github.com/vortex-data/vortex/pull/10314) stay open, and the work ignores them for now | Small PRs are easier to review, but not when a split needs temporary code or changes file contents twice. In one release, writers that select the preview edition never pay the `i256` cost of D17 |
| D12 | Each precision has the smallest signed width that holds its values: `i8` for precision 1 to 2, `i16` for 3 to 4, `i32` for 5 to 9, `i64` for 10 to 18, `i128` for 19 to 38 and `i256` for 39 to 76. `DecimalDType::canonical_values_type()` owns the mapping. Its name differs from the stored-width accessor `DecimalArray::values_type()`, so code cannot mix the two up. This settles DQ1 | It is the existing `smallest_decimal_value_type`. From precision 5, it is the width of the smallest Arrow decimal type that holds the precision |
| D13 | Imports copy into the canonical width. They write zeros in null slots, and they fail on a value outside the precision. The Arrow import logic can be configured to handle such values in another way. For an export at a wider dtype, Vortex executes a `Widen` over the array | arrow-rs does not check decimal values when it builds an array. An error is better than a silent change of the data |
| D14 | `DecimalArray::try_new` checks the width and every valid value, with an `ExecutionCtx` (D30). `new_unchecked` skips the value check, for kernels that keep values legal. File reads trust the precision and never panic | This is the rule of X7 for decimals, and the recommendation XQ3 for file reads |
| D15 | `Widen` kernels pass work to the child, with canonicalization as the fallback. A `Widen` over a `Widen` becomes one `Widen`. A cast of a `Widen` passes to the child with the same target dtype, except that a wider integer target returns a `Widen` over the child. Another decimal cast to a precision with the same scale returns a `Widen` when the canonical width grows, changes only the dtype when the width stays, and checks every value when the precision drops | A `Widen` holds exactly the values of its child, so work on the child gives the same result on less data |
| D16 | In DecimalByteParts, the MSP is any signed integer up to 64 bits, and every lower part has the dtype `u64`. The constructor and the module doc become stricter, and the constructor rejects lower parts that assemble wider than the canonical width (D29). This settles DQ4. Operations run on the parts wherever they can. Decoding returns the canonical array of the DecimalByteParts dtype or a decimal `Widen`. The parts assemble at their natural width: the MSP width with no lower parts, `i128` with one lower part, and `i256` with two or three. `WidenArray::from_stored_decimal` (D40) then picks the result. For a lone MSP that is not at the canonical width, the range comes from `min_max` on the MSP, which returns exact cached statistics or makes one vectorized pass. The range is passed as an exact range, so the child records exact extrema. A lone MSP at the canonical width needs no range, and the helper scans values assembled from lower parts. The GPU still decodes to the canonical width, because CUDA has no `Widen` kernel. The `Widen` result was the later work LT2, which is now part of CD5 | A narrow MSP needs no conversion at read time. The stricter constructor breaks no file, because no file has lower parts: no edition permits v2, and its compat fixture is disabled. The compressor never narrows the dtype of a lower part. The first version of #10905 widened every narrow MSP with a copy, and CodSpeed showed regressions of up to 11x. A `Widen` reuses the narrow MSP buffer, as `develop` does today. The decimal `valid_range` scan is not vectorized, so the MSP range comes from the integer `min_max` |
| D17 | The compressor has one DecimalByteParts scheme. The scheme takes the canonical array, uses the value range to choose the number of lower parts, and narrows the MSP dtype as the compressor narrows every internal child. This replaces `narrowed_decimal` and keeps file contents, except that large values in null slots can give a narrower MSP. The scheme stays after the wire change, for writers whose edition does not permit `vortex.widen`. When an edition permits `vortex.widen`, a `Narrow` scheme runs before it and narrows the decimal type first (D33). In an edition without the lower-parts format, precision 39 to 76 with values that need more than 64 bits is written as a plain `i256` array. The `core` family holds the formats of the default writer, so default writers pay this cost until both formats enter `core` | The canonical fix makes a narrow decimal array illegal in memory, so the scheme cannot call `narrowed_decimal`. File contents do not change before the wire change. The `i256` cost affects only very wide decimals with values above 64 bits. The only way around it writes the old narrow form into new files, and it needs a special serializer |
| D18 | `vortex.widen` stays in memory only until the maintainer decides to write it to files. Every new wire format enters a preview edition before `core`. `vortex.widen` and DecimalByteParts with lower parts enter one preview edition together, and later `core` together. Other IDs can join that edition, but this plan adds only these two. This settles DQ9 | In-memory changes land first, so the edition change stays small |
| D19 | The bar of no compute regression applies to the final state, not to the steps in between. Missing benchmarks land before the changes that they cover. A gap column holds values that fit a width but need the precision of the next width. In the final state, such a column uses the wider width in memory, and that cost is accepted. Pushdown of sum, min and max into the MSP can come later | A true child label needs the next width for such values. Disk size and exports do not change |
| D20 | The canonical decimal work does not include the integer view, wide integers, FixedSizeBinary, decimal arithmetic across precisions and scales, casts that lose information, or the lower bound of a negative scale. Their recommendations are unreviewed future work. Epic [#10730](https://github.com/vortex-data/vortex/issues/10730) tracks wide integers and FixedSizeBinary. Issue [#9902](https://github.com/vortex-data/vortex/issues/9902) is its sub-issue for FixedSizeBinary, and wide integers get a tracking issue when that work is scheduled. The recommendation to always store min and max on the MSP (DQ8) is dropped | The canonical fix needs none of them. Stored min and max exist only on a BitPacked MSP, and a slice drops them |
| D21 | Every narrowing copy writes zeros in null slots, and it fails on a valid value outside the precision of the target dtype. The reads make such a copy when the stored width is wider than the width of the result: a canonical array or a `Widen` child. This happens for old nodes, and for DecimalByteParts decoding whose natural width (D16) is wider than the width of the result. All of these copies go through `WidenArray::from_stored_decimal` (D40). A read without a copy trusts the precision and does not scan | The copy reads every value anyway, so the precision check costs nothing extra, and it matches the import rule of D13. A check without a copy needs a scan that the read does not otherwise make |
| D22 | An integer `Widen` child has the same signedness and nullability as its parent, and a strictly smaller width. So an `I64` column with values from 0 to 200 gets an `I16` child, not a `U8` child | Mixed signedness needs more code in casts, in the compare shortcut and in the arithmetic bounds, and it saves at most one width. Part 1 of PR [#10333](https://github.com/vortex-data/vortex/pull/10333) also keeps the signedness of internal buffers |
| D23 | `vortex.widen` is only for columns with a fixed logical dtype: decimal columns and top-level integer columns. Which arrays the compressor wraps in a `Widen` is deferred (D27). Internal integer children keep changing their own dtype, through the deprecated `encode_values` (D28). These include list offsets, dictionary codes, run ends, patch and sparse indices, `DateTimeParts`, VarBin and FSST offsets, and the DecimalByteParts MSP. Whether `List` and `ListView` offsets get a fixed `I64` dtype with `Widen` is an open question on issue [#10733](https://github.com/vortex-data/vortex/issues/10733), and the decimal work does not depend on it | The parent chooses the dtype of an internal child, so the child can narrow its dtype without a `Widen`. A column has a dtype that the user chose |
| D24 | The compat fixtures are published from a release before the PRs that change how files are read (D31), because only the old writer can make narrow leaves. They cover only reads that succeed: narrow, wide and Arrow-style widths, gap values, high scales at narrow widths, nonzero values in null slots, and DecimalByteParts with a narrow MSP. Error cases, such as a value outside the precision in a narrowing copy, are unit tests | The compat harness (`vortex-test/compat-gen`) expects the current reader to read every published fixture |
| D25 | Generic structural encodings always sit above `Widen`. Reduce rules move `Dict`, `RunEnd`, `Sparse`, `Constant`, `Masked`, `Chunked` and `Interleave` above a `Widen`. The chunked and interleave merge rules of the local rewrite, which put `Widen` on top, are dropped. A follow-up issue covers the same rule for every encoding | The Arrow and DuckDB exporters and the dict layout look for these encodings at the root. One direction for every rule cannot loop |
| D26 | CD4 lowers a `Widen` to its canonical array in `ArraySerializationTree::try_new` (`vortex-array/src/serde.rs`). It executes the `Widen` to `RecursiveCanonical`, and the result inherits the statistics of the `Widen`. The lowering is crate-private, adds no public API, and applies to `Widen` only. It runs before the plugin lookup, and the recursion over the children lowers a nested `Widen`. A `TODO(connor)[Widen]` marks it. When `vortex.widen` gets a wire form (WR1), the lowering stays only for contexts that do not permit that ID. LT1 decides its end. `ArraySession` does not register `Widen` until WR1 gives it a wire form, because a registered `VTable` also gets a reader entry under `vortex.widen` that can only fail, which hides the `allow_unknown` foreign fallback and lists the ID in footers written without editions. Until WR1, `Widen::serialize` panics with a `TODO(connor)[Widen]`, and the lowering keeps the serializer from calling it | After CD4, a widening decimal cast returns a `Widen`, so IPC and writers without a compressor meet one in ordinary use. After CD5 and CD6, reads of narrow DecimalByteParts columns and of old nodes return one too. IPC, flat writes, the CUDA layout, Python `serialize` and pickling all pass through `try_new`. The lowered nodes intern only `vortex.decimal`, `vortex.primitive` and `vortex.bool`, so a context that does not permit `vortex.widen` accepts them, and footers never list it. The default file writer needed no lowering, because the compressor canonicalizes its input. Python `__vortex_array_metadata__` calls `array_serialize` directly, so the lowering does not cover it |
| D27 | Which arrays the compressor narrows is deferred to the design pass of WR3 | The candidates include struct fields, list elements, extension storage, and arrays that layouts create, such as dict-layout codes and zone maps |
| D28 | `Widen` has `encode`, which builds a `Widen`, and `encode_values`, which returns only the narrowed child with the same signedness. `encode_values` is `#[deprecated]`. It replaces `PrimitiveArrayExt::narrow` at every call site, and each call carries `#[expect(deprecated)]` with a `TODO(connor)` reason. The PR that moves the call sites checks that the latest release reads the files that it writes | Every narrowing that changes a dtype is then marked for a later decision. Readers on `develop` accept signed internal children |
| D29 | The DecimalByteParts constructor rejects a lower-part count whose assembled width is wider than the canonical width. Precision up to 18 allows no lower parts, 19 to 38 at most one, and 39 to 76 any count | Decoding then never needs a narrowing copy after assembly. No file breaks, because no edition permits lower parts |
| D30 | `DecimalArray::try_new` takes an `ExecutionCtx`, because the value check reads the validity, which can be lazy. Imports check their own values against the Arrow null buffer and then use the unchecked constructors, so a zero-copy import scans once | This follows `VarBinViewArray::try_new`, and it keeps the context out of the import API |
| D31 | Library changes land first. Only the PRs that change how files are read, CD5 (DecimalByteParts decoding) and CD6 (the read plugin), wait for the compat fixtures. | D36 | An operation on a `Widen` fails only where the same operation on the parent dtype fails, and it gives the same result. A kernel can run the same aggregate on the child and widen the child partial to the partial dtype of the parent, but only for an aggregate where decoding gives the same result. For integers these are `MinMax`, `Min`, `Max`, `IsConstant`, `IsSorted`, and `Sum` when the batch cannot overflow and the accumulator sums each batch from zero. Every other aggregate keeps the default path | `Widen` is a physical encoding, so it must not change behavior. Integer decoding is strictly increasing, one-to-one and keeps validity, so these partials widen exactly, and the child runs the same accumulator code, so edge cases match by construction. A decimal sum checks overflow at the precision of its input, so a child sum can overflow before the parent sum, and decimals need their own argument. `Sum` with `skip_nans` has the legacy `Stat::Sum` bridge, which sums each batch from zero. So the decimal kernel makes the same checked adds as the canonical batch, and its result is exact. Without the bridge, the canonical batch adds to the running sum, and the precision check runs only at the end. A kernel that sums the batch alone can then fail where the canonical batch does not. A running sum near the bound of `Decimal(13, 0)`, the sum dtype of `Decimal(3, 0)`, is a counterexample. A child from `from_stored_decimal` records its extrema (D40), so `MinMax` needs no scan |

## Casts

### Settled

| ID | Decision | Reason |
| --- | --- | --- |
| C1 | A cast between two dtypes exists only if a rule for that pair exists. Vortex ships rules for common pairs of built-in types, as the Rust standard library ships `From` implementations. Reading storage as another type is never a cast | Opt-in conversions with good defaults. Today casts reinterpret storage and disagree between paths |
| C2 | Every cast that the extension work adds is exact. `Timestamp(ms)` to `Timestamp(ns)` is a cast that fails on overflow. `Timestamp(ns)` to `Timestamp(ms)` is not a cast: a named function with an explicit rounding mode does it. This settles CQ1 for extension types | Vortex moves away from casts that can lose information. The lossy primitive casts below are a known issue, out of scope for now |

Known issue, not specific to extension types: primitive casts check only the range of a value. When
a conversion is not always lossless, `cast_values` uses `NumCast::from`
(`vortex-array/src/arrays/primitive/compute/cast.rs` at `c56ee8803b`). So a float to integer cast
truncates toward zero, an integer to float cast rounds, and an `f64` to `f32` cast rounds and turns
a finite value outside the `f32` range into infinity. None of these returns an error. They get
fixed when the work meets them.

### Open

| ID | Question | Recommendation |
| --- | --- | --- |
| CQ1 | What does the default cast do with a value that it cannot represent exactly? | It returns an error, like `TryFrom`. Lossy steps such as `trunc` and `round` are separate, named expressions. C2 settles this for extension types. For decimals, this is future work (D20). The primitive casts are a known issue |
| CQ2 | How do struct casts match fields? | By name, with unique field names (issue [#6900](https://github.com/vortex-data/vortex/issues/6900)). Extra source fields return an error |
